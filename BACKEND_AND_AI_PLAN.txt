PROJECT OVERVIEW
----------------
ThermaMind AI is a warehouse climate management platform with 4 frontend screens:
  1. Dashboard     — Live sensor data (temp, humidity, CO2, occupancy, efficiency)
  2. Energy        — HVAC optimization, carbon reduction, fan/compressor controls
  3. Insights      — Climate stability score, occupancy forecasting, AI recommendations
  4. Schedule      — Global target profiles, daily schedules, forecast simulation

Current backend: Bare Express + Socket.IO server emitting random-walk mock data.
Database: PostgreSQL via Prisma (SensorData, SystemStatus models defined).

1.2 EXTENDED PRISMA SCHEMA
--------------------------
model User {
  id        Int      @id @default(autoincrement())
  email     String   @unique
  name      String
  role      String   @default("operator")  // operator | admin
  createdAt DateTime @default(now())
}

model Zone {
  id          Int          @id @default(autoincrement())
  name        String       @unique   // "Storage Zone A", "Packaging Section"
  type        String                 // "storage", "packaging", "cold_storage"
  sensorData  SensorData[]
  alerts      Alert[]
  schedules   Schedule[]
}

model SensorData {
  id          Int      @id @default(autoincrement())
  zoneId      Int
  zone        Zone     @relation(fields: [zoneId], references: [id])
  temperature Float
  humidity    Float
  co2         Float
  occupancy   Int
  airflow     Float    @default(0)
  timestamp   DateTime @default(now())
  @@index([zoneId, timestamp])
}

model SystemStatus {
  id             Int      @id @default(autoincrement())
  efficiency     Float
  load           Float    // kW
  coolingScore   Float
  carbonSaved    Float    @default(0)
  fanSpeed       Float    @default(65)
  compressorEff  Float    @default(94)
  timestamp      DateTime @default(now())
}

model Alert {
  id          Int      @id @default(autoincrement())
  zoneId      Int
  zone        Zone     @relation(fields: [zoneId], references: [id])
  type        String   // "humidity_rise", "temp_spike", "co2_high", "occupancy_surge"
  severity    String   // "info", "warning", "critical"
  message     String
  isAcked     Boolean  @default(false)
  createdAt   DateTime @default(now())
}

model Schedule {
  id          Int      @id @default(autoincrement())
  zoneId      Int
  zone        Zone     @relation(fields: [zoneId], references: [id])
  name        String   // "Active Operational Shift"
  startTime   String   // "06:00"
  duration    Int      // hours
  targetTemp  Float
  targetHum   Float
  mode        String   // "full_load", "standby", "eco"
  isActive    Boolean  @default(true)
  createdAt   DateTime @default(now())
}

model AIRecommendation {
  id          Int      @id @default(autoincrement())
  type        String   // "airflow_redirect", "pre_cool", "setback"
  message     String
  confidence  Float
  savings     Float    // percentage
  applied     Boolean  @default(false)
  createdAt   DateTime @default(now())
}

model EnergyLog {
  id             Int      @id @default(autoincrement())
  hvacLoad       Float    // kW
  optimizedLoad  Float    // kW (after AI optimization)
  savingsPercent Float
  carbonReduced  Float    // kg CO2
  timestamp      DateTime @default(now())
  @@index([timestamp])
}

  "sensor_update"       — Every 2s, live sensor data per zone

  "set_fan_speed"       — { zoneId, speed: "low"|"balanced"|"industrial"|"peak" }

2.2 AI MODEL DETAILS
---------------------

MODEL 1: OCCUPANCY FORECASTER (Feeds → Insights Screen)
  Purpose:  Predict warehouse zone occupancy 15-60 minutes ahead
  Type:     LSTM (Long Short-Term Memory) neural network
  Input:    [timestamp, zone, historical_occupancy (24h), day_of_week, hour]
  Output:   Predicted occupancy count for next 4 intervals (15min each)
  Training: Synthetic data simulating warehouse shift patterns
  Library:  PyTorch
  Endpoint: POST /predict/occupancy
  Request:  { "zone_id": 1, "horizon_minutes": 60 }
  Response: { "predictions": [12, 18, 24, 20], "confidence": 0.94 }

MODEL 2: COOLING DEMAND PREDICTOR (Feeds → Energy Screen)
  Purpose:  Forecast HVAC energy demand based on conditions
  Type:     XGBoost regression
  Input:    [temp, humidity, co2, occupancy, external_temp, time_of_day]
  Output:   Predicted kW load for next hour
  Training: Synthetic sensor data with seasonal patterns
  Library:  XGBoost + scikit-learn
  Endpoint: POST /predict/demand
  Request:  { "zone_id": 1, "current_conditions": {...} }
  Response: { "predicted_load_kw": 14.8, "optimal_load_kw": 11.2, "savings": 24.3 }

MODEL 3: ANOMALY DETECTOR (Feeds → Dashboard Alerts)
  Purpose:  Detect unusual sensor patterns (temp spikes, CO2 surges)
  Type:     Isolation Forest + threshold rules
  Input:    [temp, humidity, co2, occupancy, airflow] (rolling 30min window)
  Output:   Anomaly score (0-1) + anomaly type classification
  Library:  scikit-learn
  Endpoint: POST /detect/anomaly
  Request:  { "zone_id": 1, "readings": [...last_15_readings] }
  Response: { "is_anomaly": true, "score": 0.87, "type": "humidity_rise",
              "message": "Humidity rising in Storage Zone A..." }

MODEL 4: RL HVAC OPTIMIZER (Feeds → Energy Screen + Dashboard)
  Purpose:  Optimize HVAC setpoints to minimize energy while maintaining comfort
  Type:     Deep Q-Network (DQN) reinforcement learning agent
  State:    [temp, humidity, co2, occupancy, external_temp, current_setpoint,
             fan_speed, time_of_day, energy_price]
  Actions:  [increase_cooling, decrease_cooling, increase_fan, decrease_fan,
             maintain, eco_mode, boost_mode]
  Reward:   - energy_consumed * 0.4
            - abs(temp - target_temp) * 0.3
            - abs(humidity - target_humidity) * 0.2
            + comfort_score * 0.1
  Library:  PyTorch + Stable-Baselines3
  Endpoint: POST /optimize/hvac
  Request:  { "zone_id": 1, "current_state": {...}, "target": {...} }
  Response: { "action": "decrease_cooling", "new_setpoint": 22.8,
              "fan_speed": 65, "predicted_savings": 12.5,
              "efficiency_score": 98.2 }

MODEL 5: RECOMMENDATION ENGINE (Feeds → Insights Screen AI Card)
  Purpose:  Generate human-readable operational recommendations
  Type:     Rule-based engine + Gemini API for natural language generation
  Input:    Outputs from Models 1-4 + current system state
  Output:   Prioritized recommendations with confidence/savings
  Endpoint: POST /recommend
  Request:  { "zone_id": 1 }
  Response: { "recommendation": "Occupancy predicted to increase...",
              "confidence": 0.94, "savings_percent": 12.5,
              "co2_trend": "stable", "type": "airflow_redirect" }

3.2 DATA FLOW — REALTIME LOOP
------------------------------
Every 2 seconds:
  1. Sensor Ingest generates/receives sensor readings
  2. Data saved to PostgreSQL via Prisma
  3. Readings sent to Anomaly Detector → returns anomaly status
  4. If anomaly → Alert created + pushed via Socket.IO "alert_triggered"
  5. Sensor data pushed via Socket.IO "sensor_update" to all clients

Every 30 seconds:
  6. Batch of recent readings sent to RL Optimizer
  7. RL agent returns optimal HVAC action
  8. SystemStatus updated (efficiency, load, cooling score)
  9. Energy savings computed and logged to EnergyLog
  10. System status pushed via Socket.IO "system_status"

Every 5 minutes:
  11. Occupancy Forecaster generates predictions for next hour
  12. Demand Predictor forecasts energy needs
  13. Recommendation Engine combines all model outputs
  14. AIRecommendation record created
  15. Pushed via Socket.IO "ai_recommendation"

4.1 SENSOR SIMULATOR (replaces current random walk)
----------------------------------------------------
File: backend/src/services/sensorSimulator.ts

Features:
  - Realistic multi-zone simulation (3 zones: Storage A, Packaging, Cold Storage)
  - Time-of-day patterns (higher occupancy 06:00-14:00, lower at night)
  - Seasonal temperature influence
  - Occupancy-driven CO2 and humidity correlation
  - Random events (door opening → temp spike, shift change → occupancy surge)
  - Configurable via .env for demo vs production mode

4.2 DATA RETENTION POLICY
--------------------------
  - Raw sensor data: Keep 30 days, then downsample to 1-hour averages
  - Energy logs: Keep 1 year
  - Alerts: Keep 90 days
  - AI recommendations: Keep 30 days
  - Implement via node-cron job running daily at 02:00

5.1 THRESHOLD-BASED ALERTS
---------------------------
  Temperature > 25°C or < 18°C        → WARNING
  Temperature > 28°C or < 15°C        → CRITICAL
  Humidity > 60% or < 30%             → WARNING
  CO2 > 800 ppm                       → WARNING
  CO2 > 1000 ppm                      → CRITICAL
  Occupancy > zone_capacity * 0.9     → WARNING

5.2 AI-DRIVEN ALERTS
---------------------
  Anomaly detector score > 0.7        → WARNING (with ML-generated message)
  Anomaly detector score > 0.9        → CRITICAL
  Occupancy forecast predicts surge   → INFO (pre-emptive)

KEY TECHNOLOGY DECISIONS
================================================================================

1. Node.js backend (not Python) — keeps consistency with existing server.js,
   Socket.IO runs natively, REST API is straightforward.

2. Separate Python microservice for AI — PyTorch/scikit-learn ecosystem is
   far superior for ML. Node calls Python via HTTP (axios → FastAPI).

3. PostgreSQL — already configured via Prisma. Excellent for time-series
   queries with proper indexing. TimescaleDB extension possible later.

4. Gemini API for NLG — generates natural language recommendations from
   raw model outputs. Keeps recommendations contextual and readable.

5. DQN over PPO for RL — simpler to train with discrete action space,
   more stable for the HVAC control problem at this scale.
